# 문제 재정의 기반 의사결정

## Overview

작아진 채 전달된 문제를 곧바로 해결하지 않는다. 먼저 관찰된 증상과 해석을 분리하고, 상위 목적·앞단·뒷단·이해관계자·시간축으로 문제의 경계를 넓힌다. 이후 최소 3단계의 연쇄 효과를 추적하고, 재정의된 문제를 기준으로 대안을 비교한다.

큰 그림은 모든 것을 조사하는 일이 아니다. **현재 결정의 파급 범위를 설명하고 안전하게 실행할 수 있을 만큼만 경계를 넓히는 것**이다. 분석 비용이 위험보다 커지지 않도록 결정의 가역성과 피해 규모에 따라 깊이를 조절한다.

이 스킬은 좋은 결과와 좋은 판단 과정을 분리해서 평가한다. 결과적으로 문제가 해결됐더라도 최초 문제 정의의 오류, 놓친 신호, 운이 좋았던 부분, 재발 방지 장치를 별도로 남긴다.

## When to Use

다음 중 하나라도 해당하면 사용한다.

- 문제가 한 문장이나 한 증상으로 작게 잘려서 전달됐다.
- 바로 떠오르는 해결책이 있지만 다른 시스템이나 사람에게 영향이 갈 수 있다.
- 정산·잔고·결제·배치·보고·권한·데이터 수정처럼 연쇄 효과가 큰 작업이다.
- 임시 수정이 다음 배치, 야간·휴일 운영, 외부 보고에 영향을 줄 수 있다.
- 같은 문제가 반복되거나 이전 해결 뒤 예상하지 못한 후속 장애가 생겼다.
- 누군가가 무능하거나 지엽적으로 사고한다고 판단하고 있다.
- 해결은 됐지만 의사결정 과정이 건전했는지 별도로 회고해야 한다.
- 사용자 또는 팀이 “문제를 넓혀서 다시 정의해 달라”고 요청한다.

다음에는 전체 절차를 사용하지 않는다.

- 영향 범위가 명확한 단순·가역 작업: 빠른 5분 점검만 사용한다.
- 이미 승인된 실행 절차를 그대로 수행하는 작업: 절차의 전제나 환경이 달라졌을 때만 재정의한다.
- 즉시 복구가 최우선인 장애 대응: 먼저 피해를 완화하되, 완화책의 파급 범위와 사후 재정의를 반드시 기록한다.
- 사람의 성격이나 능력을 판정하는 용도: 관찰 가능한 행동과 시스템 조건을 분석한다.

## Operating Principles

### 1. 해결보다 문제 정의가 먼저다

최초 문제 문장은 입력이지 결론이 아니다. “무엇을 고칠까?”보다 먼저 “지금 정의한 문제가 진짜 문제인가?”를 묻는다.

### 2. 사실·해석·가정·평가를 분리한다

- **사실:** 로그, 수치, 시간, 실행 결과, 직접 들은 말처럼 확인 가능한 정보
- **해석:** 사실이 의미한다고 생각하는 바
- **가정:** 아직 확인하지 않았지만 의사결정이 의존하는 조건
- **평가:** 사람이나 과정의 능력·품질에 대한 판단
- **감정:** 조급함, 답답함, 확신, 쾌감처럼 탐색을 멈추거나 넓히게 하는 상태

평가를 사실처럼 쓰지 않는다. `담당자가 무능하다` 대신 `담당자가 앞단과 뒷단을 확인하지 않은 채 같은 설명을 반복했다`처럼 관찰 가능한 형태로 바꾼다.

### 3. 큰 그림의 범위는 위험에 비례한다

- **낮은 위험·가역적:** 5분 점검 후 실행
- **중간 위험:** 범위 지도, 대안 2개 이상, 검증·롤백 조건 기록
- **높은 위험·비가역적:** 이해관계자 확인, 독립 검토, 단계적 실행, 승인, 조기 경보와 롤백 계획 필수

### 4. 국소 최적화보다 전체 불변 조건을 지킨다

숫자 하나를 맞추는 것과 시스템 전체가 설명 가능한 것은 다르다. 먼저 이 업무가 반드시 지켜야 하는 불변 조건을 한 문장으로 쓴다.

예: `동일한 기준 시각과 범위에서 원장·지갑·보고 잔고의 차이가 설명 가능해야 한다.`

### 5. 결과와 과정을 따로 평가한다

- 결과가 좋고 과정도 좋음: 재사용한다.
- 결과는 좋지만 과정이 나쁨: 운 또는 사후 수습이 개입했는지 확인하고 안전장치를 만든다.
- 결과는 나쁘지만 과정이 좋음: 불확실성과 모델 한계를 갱신한다.
- 결과와 과정이 모두 나쁨: 문제 정의부터 다시 시작한다.

## Workflow

### Step 0. 위험도와 시간 예산 설정

먼저 아래를 확인한다.

- 이 결정은 되돌릴 수 있는가?
- 잘못됐을 때 피해가 사용자·재무·법무·보안·외부 보고로 번지는가?
- 야간이나 휴일에 사람을 호출할 수 있는가?
- 지금 복구가 먼저인가, 분석이 먼저인가?

시간 예산을 정한다.

- 낮은 위험: 5분
- 중간 위험: 15~30분
- 높은 위험: 필요한 검토와 승인이 끝날 때까지 실행 보류. 단, 피해 완화는 별도 수행

**완료 기준:** 위험 수준, 가역성, 분석 시간 예산이 기록돼 있다.

### Step 1. 최초 문제를 한 문장으로 고정

전달받은 표현을 고치지 말고 먼저 그대로 쓴다.

```markdown
최초 문제: 잔고대사가 맞지 않는다.
요청받은 조치: 어긋난 숫자의 원인을 찾아 수정한다.
```

이 단계에서 해결책을 문제 문장에 섞지 않는다. `캐시를 비워야 한다`는 문제 정의가 아니라 해결 가설이다.

**완료 기준:** 증상과 요청된 조치가 각각 한 문장으로 분리돼 있다.

### Step 2. 사실·해석·가정·평가·감정 분리

```markdown
확인된 사실:
- 

현재 해석:
- 

검증하지 않은 가정:
- 

사람·과정에 대한 평가:
- 

판단에 영향을 줄 수 있는 감정:
- 
```

감정은 제거 대상이 아니라 조기 종결 신호다. `역시 간단한 문제다`, `내가 맞았다`, `왜 이것도 못하지`라는 생각이 들면 해결책 실행 전에 반증 질문을 하나 추가한다.

**완료 기준:** 의사결정이 의존하는 모든 핵심 가정이 사실 목록과 분리돼 있다.

### Step 3. 상위 목적과 불변 조건 확인

다음 질문에 답한다.

1. 이 업무가 존재하는 이유는 무엇인가?
2. 지금의 국소 문제보다 한 단계 위의 목적은 무엇인가?
3. 어떤 조건은 해결 전후에도 반드시 참이어야 하는가?
4. 숫자나 화면만 맞으면 되는가, 원인과 흐름도 설명 가능해야 하는가?

```markdown
상위 목적:
불변 조건:
현재 최적화하려는 국소 지표:
국소 최적화가 전체에 만들 수 있는 손해:
```

**완료 기준:** 상위 목적 1개와 검증 가능한 불변 조건 1개 이상이 있다.

### Step 4. 다섯 축으로 문제 경계 확장

| 축 | 확인 질문 |
|---|---|
| 시간 | 이전 상태·현재 조치·다음 배치·마감·야간·휴일에는 무엇이 달라지는가? |
| 흐름 | 이 문제의 입력은 어디서 오고 출력은 어디로 가는가? 앞단과 뒷단은 무엇인가? |
| 시스템 | 어떤 서비스·DB·원장·파일·외부 API·수동 절차가 연결되는가? |
| 사람 | 누가 만들고, 승인하고, 보고받고, 대응하고, 호출되는가? |
| 범위 | 어떤 고객·계정·자산·기간·환경·예외 케이스가 포함되거나 제외되는가? |

간단한 흐름 지도를 만든다.

```text
원천 → 변환·집계 → 계산 → 대사 → 보고 → 보고를 보고 행동하는 사람
```

각 노드에 `입력/출력`, `담당자`, `실패 시 다음 단계에 보이는 증상`을 붙인다.

**완료 기준:** 최소한 앞단 1개, 뒷단 1개, 직접 이해관계자, 간접 이해관계자, 다음 시간대의 영향이 식별돼 있다.

### Step 5. 연쇄 효과를 최소 3단계 추적

각 대안에 대해 다음 문장을 세 번 반복한다.

```text
이 조치를 하면 → 다음에 누가/무엇이 어떻게 반응한다 → 그 결과 무엇이 다시 발생한다
```

반드시 확인할 질문:

- 다음 배치나 다음 보고에서도 같은 설명이 성립하는가?
- 누군가 수동으로 후속 조치를 해야 하는가?
- 그 사람은 필요한 맥락과 권한을 갖고 있는가?
- 실패하면 야간·휴일에 누가 호출되는가?
- 문제를 해결한 것이 아니라 다른 위치나 시간으로 옮긴 것은 아닌가?
- 정상 경로뿐 아니라 지연·중복·부분 실패·재시도에서는 어떻게 되는가?

**완료 기준:** 1차·2차·3차 효과와 가장 위험한 실패 경로가 기록돼 있다.

### Step 6. 반증 탐색과 대안 문제 정의 생성

최초 해석을 지지하는 정보만 찾지 않는다. 아래 질문 중 최소 2개에 답한다.

- 내 해석이 틀렸다면 어떤 증거가 보여야 하는가?
- 지금 관찰된 증상을 만들 수 있는 다른 원인은 무엇인가?
- 문제를 반대로 정의하면 어떤 설명이 가능한가?
- 오늘 밤 또는 다음 보고에서 다시 깨진다면 어떤 경로일까?
- 내가 비판하는 것과 같은 지엽적 사고를 지금 나도 하고 있지 않은가?

최소 3개의 문제 정의를 만든다.

```markdown
A. 최초 정의:
B. 상위 목적 중심 정의:
C. 흐름·이해관계자 중심 정의:
```

좋은 재정의는 해결책을 미리 고정하지 않고, 원인·범위·목적을 조사할 여지를 남긴다.

**완료 기준:** 최초 정의와 다른 대안 정의가 2개 이상 있고, 각 정의가 어떤 증거로 기각될 수 있는지 적혀 있다.

### Step 7. 재정의된 문제 선택

다음 기준으로 비교한다.

| 기준 | 질문 |
|---|---|
| 설명력 | 관찰된 사실을 빠짐없이 설명하는가? |
| 범위 | 실제 영향을 받는 시스템과 사람을 포함하는가? |
| 검증 가능성 | 맞고 틀림을 확인할 수 있는가? |
| 중립성 | 특정 해결책이나 사람 탓을 결론으로 넣지 않았는가? |
| 행동 가능성 | 다음 조사나 결정을 구체적으로 이끄는가? |
| 비용 적정성 | 문제를 필요 이상으로 키우지 않았는가? |

```markdown
재정의된 문제:
이 정의를 선택한 근거:
제외한 범위와 이유:
아직 남은 불확실성:
```

**완료 기준:** 한 문장의 재정의된 문제와 의도적으로 제외한 범위가 명시돼 있다.

### Step 8. 대안을 네 종류로 만든다

하나의 해결책에 고착되지 않도록 다음을 각각 고려한다.

1. **국소 해결:** 지금 보이는 증상을 빠르게 완화
2. **구조적 해결:** 원인이나 시스템 구조를 변경
3. **안전장치:** 모니터링, 검증, 승인, 알림, 런북 추가
4. **보류·조사:** 결정 전에 최소 정보만 추가 확인

각 대안에 대해 기록한다.

```markdown
대안:
해결하는 범위:
해결하지 못하는 범위:
기대 효과:
비용과 부작용:
가역성:
필요한 사람·승인:
검증 방법:
```

**완료 기준:** 실행 가능한 대안이 2개 이상이며, 최소 1개는 현재 떠오른 국소 해결과 다른 종류다.

### Step 9. 결정과 안전장치 기록

```markdown
결정:
목적:
선택 근거:
기각한 대안과 이유:
담당자와 기한:
실행 전 확인:
성공 신호:
조기 경보:
중단 조건:
롤백 방법:
야간·휴일 연락 경로:
의사결정 시각과 재검토 시각:
```

가역적인 결정은 작게 실행하고 관찰한다. 비가역적이거나 피해 규모가 큰 결정은 독립 검토와 승인을 거친다.

**완료 기준:** 성공·실패를 구분할 신호, 중단 조건, 롤백 또는 피해 완화 방법이 모두 있다.

### Step 10. 결과와 판단 과정 사후 회고

결과가 좋았다는 이유로 판단 과정의 오류를 지우지 않는다.

```markdown
실제 결과:
최초 예상과 달랐던 점:
놓친 사실·가정·이해관계자:
조기 신호가 있었는가:
결과가 좋았어도 운이 좋았던 부분:
결과의 품질:
판단 과정의 품질:
다음에 추가할 문서·체크·역할·알림:
```

사람에 대한 평가를 재발 방지책으로 끝내지 않는다. 반복 가능한 장치로 바꾼다.

- 기억해야 한다 → 체크리스트 또는 자동 검증
- 설명해야 한다 → 런북, 예시, 인수인계, 소유자 명시
- 확인해야 한다 → 모니터링, 알림, 승인 단계
- 특정 사람만 안다 → 문서화와 교차 훈련

**완료 기준:** 결과와 과정이 별도 평가됐고, 다음 사건 전에 적용 가능한 예방 장치가 최소 1개 있다.

## Fast Path: 5분 문제 확장

낮은 위험이거나 즉시 판단해야 할 때는 아래만 작성한다.

```markdown
보이는 증상:
본래 목적·불변 조건:
앞단 / 뒷단:
영향받는 사람·시스템·다음 시간대:
미검증 가정:
이 해결이 틀리면 오늘 밤 또는 다음 보고에서 깨질 것:
재정의된 문제:
결정 / 성공 신호 / 롤백:
```

아홉 줄을 모두 채우지 못해도 빈칸을 숨기지 않는다. `모름`은 추가 확인이 필요한 위험 정보다.

## Output Format

사용자가 별도 형식을 요청하지 않으면 다음 순서로 제시한다.

```markdown
# 의사결정 기록

## 1. 최초 문제
- 증상:
- 요청된 조치:

## 2. 사실과 불확실성
- 확인된 사실:
- 해석:
- 가정:
- 사람·과정에 대한 평가:

## 3. 확장된 경계
- 상위 목적·불변 조건:
- 앞단·뒷단:
- 시스템·사람·시간축:
- 1차·2차·3차 효과:

## 4. 문제 재정의
- 최초 정의:
- 대안 정의:
- 선택한 정의:
- 제외한 범위:

## 5. 대안과 결정
- 대안 비교:
- 결정과 근거:
- 성공 신호:
- 조기 경보·중단·롤백:

## 6. 사후 회고
- 실제 결과:
- 결과의 품질:
- 판단 과정의 품질:
- 예방 장치:
```

확인되지 않은 내용은 `추정`, `가정`, `미확인`으로 표시한다. 타인의 의도·능력·반응을 사실처럼 쓰지 않는다.

## Worked Example: 잔고대사 문제

아래 예시는 사용자가 제공한 사건의 판단 구조만 사용한다. 구체적인 원인이나 시스템 구성은 알려지지 않았으므로 만들지 않는다.

```markdown
최초 문제:
- 잔고대사가 맞지 않는다.

최초 대응의 한계:
- 문제를 지엽적으로 파악하고 해결했다.
- 그 조치가 연쇄 효과를 일으켜 새벽 전화로 이어졌다.

확인된 사실:
- 고팍스 잔고대사 문제 때문에 현장을 방문했다.
- 최초 문제 정의를 기반으로 조치했다.
- 이후 새벽 전화가 오는 상황으로 번졌다.
- 잘못 생각한 부분을 정정하고 더 큰 그림에서 재해석해 문제를 풀었다.

확인되지 않은 내용:
- 최초 조치의 정확한 내용
- 새벽 전화까지 이어진 구체적인 시스템·사람의 경로
- 최종 원인과 해결책

재정의 질문:
- 동일한 기준 시각과 범위를 사용했는가?
- 이 차이가 생성·집계·대사·보고되는 전체 흐름 중 어디서 발생했는가?
- 수정이 다음 배치와 보고 대상자에게 어떤 후속 행동을 만들었는가?
- 이 해결이 틀리다면 오늘 밤 무엇이 다시 깨지는가?

재정의된 문제의 형태:
- 특정 숫자를 맞추는 문제가 아니라, 잔고 차이가 생기고 보고되는 전체 흐름에서 기준·범위·후속 영향을 설명하고 안전하게 수정하는 문제다.
```

이 사례에서 `다른 사람들이 큰 그림을 보지 못한다`는 평가는 분석의 출발점이 될 수 있지만 결론은 아니다. 자신도 문제를 좁게 정의했다는 반례를 함께 보존하고, 개인의 무능보다 누락된 정보·역할·검증 단계·영향 분석을 먼저 찾는다.

## Common Pitfalls

1. **문제를 무한히 키운다.**
   - 수정: 현재 결정의 파급 범위와 불변 조건을 설명하는 데 필요한 축까지만 확장한다. 제외 범위를 명시한다.

2. **해결책을 문제 정의로 위장한다.**
   - 수정: `X를 해야 한다`를 가설로 옮기고, 그 조치 없이도 성립하는 문제 문장을 쓴다.

3. **분석만 하다가 실행하지 않는다.**
   - 수정: 위험도에 따라 시간 예산을 정하고, 가역적인 대안은 작게 실행해 관찰한다.

4. **사람의 무능을 원인으로 끝낸다.**
   - 수정: 어떤 행동, 정보, 역할, 목표, 검증 단계가 부족했는지 관찰 가능한 문장으로 바꾼다.

5. **정상 경로만 본다.**
   - 수정: 지연·중복·부분 실패·재시도·야간·휴일 경로를 최소 한 번 확인한다.

6. **1차 효과만 본다.**
   - 수정: `그다음에는?`을 세 번 묻고 누가 후속 행동을 해야 하는지 적는다.

7. **좋은 결과로 나쁜 과정을 덮는다.**
   - 수정: 결과 품질과 판단 과정 품질을 별도 항목으로 평가한다.

8. **모르는 값을 그럴듯하게 채운다.**
   - 수정: `미확인`으로 남기고 결정 전에 필요한 최소 정보인지 판단한다.

9. **체크리스트 완료를 사고 완료로 착각한다.**
   - 수정: 재정의된 문제를 한 문장으로 설명하고, 기존 해결책이 여전히 유효한지 다시 비교한다.

10. **과거 사건을 사후 지식으로 미화한다.**
    - 수정: 당시 알고 있던 정보와 나중에 알게 된 정보를 분리한다.

## Verification Checklist

- [ ] 최초 문제와 요청된 해결책이 분리돼 있다.
- [ ] 사실·해석·가정·평가가 구분돼 있다.
- [ ] 상위 목적과 검증 가능한 불변 조건이 있다.
- [ ] 시간·흐름·시스템·사람·범위 축을 확인했다.
- [ ] 앞단, 뒷단, 직접·간접 이해관계자를 식별했다.
- [ ] 결정의 1차·2차·3차 효과를 추적했다.
- [ ] 야간·휴일 또는 다음 배치·보고의 실패 경로를 확인했다.
- [ ] 최초 정의와 다른 문제 정의를 2개 이상 만들었다.
- [ ] 재정의된 문제가 특정 해결책이나 사람 탓을 전제하지 않는다.
- [ ] 대안이 2개 이상이며 가역성과 비용을 비교했다.
- [ ] 성공 신호, 조기 경보, 중단 조건, 롤백 방법이 있다.
- [ ] 결과와 판단 과정을 별도로 평가했다.
- [ ] 다음 사건 전에 적용 가능한 예방 장치가 최소 1개 있다.
